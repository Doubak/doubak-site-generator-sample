# doubak-site-generator-sample

[![test-scripts](https://github.com/Doubak/doubak-site-generator-sample/actions/workflows/test-scripts.yml/badge.svg?branch=main)](https://github.com/Doubak/doubak-site-generator-sample/actions/workflows/test-scripts.yml?query=branch%3Amain)

[**sample.doubak.com**](https://sample.doubak.com) —— 豆备（Doubak）生成的示例站点，数据源自作者本人的豆瓣账号。

项目主页在 **<https://doubak.com>** —— 详细介绍了本项目的整体架构与使用方法。
本仓库仅为其中一份实际产出样例。

本仓库中除本文件、`LICENSE`、`CNAME` 与 `.github/` 之外，**其余文件均由脚本自动化生成**，请勿手动修改：下次执行生成时将被全量清理并重新覆盖。

## 它是怎么来的

```sh
# 1. 浏览器扩展在本地抓取，产出 bundle（包含 WARC、索引与清单）
# 2. bundle → canonical（结构化、带修订历史）
node bin/parse.js  ~/downloads/exports ~/downloads/canonical

# 3. canonical + bundle → 本示例仓库
node bin/deploy.js ~/downloads/canonical ~/downloads/exports <这个目录> --include-private
```

**本示例站点在生成时启用了 `--include-private` 参数**，因此包含了豆瓣上未公开的内容（对应页面标记有
🔒，且在各页页脚明确提示）。示例站旨在展示该完整备份与渲染能力；**默认情况下不启用该参数，
私密日记、私密豆列以及仅自己可见的广播均不会被导出或发布**。详见「关于内容」一节。

上述三个步骤分别对应项目：[doubak-extension](https://github.com/Doubak/doubak-extension)、[doubak-data-parser](https://github.com/Doubak/doubak-data-parser)、[doubak-site-generator](https://github.com/Doubak/doubak-site-generator)。

### Sitemap 通过 GitHub Actions 自动化生成

`.github/workflows/sitemap.yml` 在每次推送到 `main` 分支后会自动重新生成 `sitemap.xml`，
并直接提交至 `main`（修改工作流顶部的 `MODE` 变量为 `pr` 即可切换为创建 PR 模式）。生成工具采用 [cicirello/generate-sitemap](https://github.com/cicirello/generate-sitemap)，
随后由 `.github/scripts/fix_sitemap.py` 进一步后处理：剔除分页中第 1 页的 meta refresh 跳转外壳，并将中日文字符标签路径按 RFC 3986 规范进行 URI 转义。
该处理脚本仅依赖 Python 标准库并附带完整测试，可通过 `python3 .github/scripts/test_fix_sitemap.py` 运行。

`deploy.js` 在重新构建站点时会保留 `.github/` 目录，避免自动化配置丢失；`sitemap.xml`
则会在部署时被清理，并在推送后由 GitHub Actions 重新生成。

**因此每次执行 `deploy.js` 之前需先执行 `git pull`。** 由于 `sitemap.xml` 是由 GitHub Actions 远端自动提交的，
本地若未同步会导致推送时遇到 non-fast-forward 冲突。

## 「什么时候 → 说了什么」

在作品详情页中，除展示当前最新的短评外，还提供了一条完整的时间线，将**标记的历次修订记录**与**提及该作品的广播内容**按时间序综合串联。

这是本项目的核心价值所在：豆瓣的标记页仅保留最新的一条短评，一旦修改便会覆盖历史；而**广播在发布后即永久固化并带有秒级时间戳**，能够完整保留标记页上早已被覆盖的历史言论，甚至包括首次备份之前的内容。

```
2026-08-01           标记 · 看过    确实还不错…之前就说能上6分…
2026-07-18 12:44:56  广播 · 想看    能上6分我觉得都是国产好片
```

未填写短评的状态演变同样属于关键历史——例如「2023-03-24 想玩 / 2023-03-31 在玩 / 2026-07-19 玩过」，即使没有文字评价，也完整记录了该条目的生命周期。

**但时间线并不妄断是否存在「编辑修改」。** 实测数据表明，在 342 条与当前短评不同的广播内容中，有 305 条属于正常的状态流转推进（如在「想看」时记录一条，看完标记为「看过」时再记录一条），仅有 15 条属于同一状态下的文本重写。若武断标记为「检测到编辑修改」，绝大多数情况下均属于误判。因此系统仅按时间顺序如实罗列，保留原始上下文供用户自行判断。

每条记录均明确标注来源出处。当时间戳与短评文字来自不同记录归并时，也会专门注明——避免出现因并列展示而让人误以为短评内容直接出自该条广播的情况。

## 搜索

站内搜索位于 [/search.html](https://sample.doubak.com/search.html)，**无需复杂的外部索引服务，无第三方依赖，也不产生任何网络请求** —— 内存全量检索耗时仅 0.1–0.5 毫秒，支持即输即显。

作品的**又名**（台译名 / 港译名 / 原文名）与标题同权重 —— 搜「重返沉默之丘」和搜「重返寂静岭」是一样的结果。导演、作者、类型也能搜（搜「宫崎骏」找得到 21 部）；主演刻意不进索引，理由详见 site-generator 的 README。

索引文件采用 `.js` 而非 `.json`：因为浏览器在 `file://` 本地协议下会拦截 `fetch` 请求，而本归档的设计目标之一是支持本地双击直接浏览。

## 两项可直接验证的工程特性

**页面打开时不发起任何外部网络请求。** 所有图片资源均已完整归档至本地，HTML 的 `src` 属性中不包含任何外部域名。这是备份的核心立足点：一份必须依赖外部联网、且必须在原平台服务存活时才能查看的数据，不能称之为真正独立的备份。

**无需启动本地 Web 服务器即可直接浏览。** 将本仓库完整下载到本地后，直接双击 `index.html` 即可查看 —— 站内所有超链接均为指向真实文件的相对路径。即使多年后从冷备份硬盘中直接读取，也能零门槛打开，而无需额外配置静态服务器环境。

## 关于内容

站点里的标记、短评、广播、日记均来自作者本人的豆瓣账号；作品封面来自豆瓣的目录数据。

**本示例中包含部分在豆瓣上未公开的内容**，这是因为生成时启用了 `--include-private` 参数 —— 用以演示私有数据的归档与渲染能力。这些内容在页面中均带有 🔒 标记：

| | |
|---|---|
| 1 篇日记 | 作者自行设置为「仅自己可见」（内容为测试文本） |
| 1 份豆列 | `SELECTS`，豆瓣上仅作者本人可见 |
| 1 条广播 | 发布上述私密日记时豆瓣自动同步生成的广播，正文与日记完全一致 |
| 1 篇日记 | **被豆瓣平台转为「仅自己可见」** —— 其原本为公开发表，页面上逐字引述了平台的说明 |

最后一行内容不受该开关限制：**默认始终导出展示**。其根本原因在于它在平台上处于非公开状态，恰恰是因为其曾是公开发表的内容；若归档备份顺从平台的隐藏策略将其抹去，备份的核心意义便荡然无存。前三项则严格受 `--include-private` 控制，**不加该参数时均不会被导出**。

关于该条私密日记同步广播的背景：在豆瓣发布私密日记时，系统会自动同步生成一条广播且正文完全一致。在用户登录态下抓取时，该条仅自己可见的广播也会被收录。此前若仅对日记页面增加可见性过滤而遗漏了广播侧，私密日记的内容仍可能通过关联广播在首页泄露。因此数据过滤逻辑必须在所有相关数据流中统一严格执行。

站点**不包含任何第三方用户数据**：抓取时严格排除他人的评论回复、关注关系与豆邮；他人转播的内容按 `data-uid` 过滤剔除；第三方上传的图片资源亦不予抓取。

## 主题支持自由更换

本示例站点采用 site-generator 内置的极简主题骨架（由 5 个文件构成的 Hugo 布局）。生成器的核心产物为标准的 **Markdown + YAML front matter**，用户若想切换为现成的 Hugo 主题，仅需替换 `layouts/` 目录；亦可灵活迁移至 Astro、Eleventy 或 Jekyll —— 详见 site-generator 的 README。
